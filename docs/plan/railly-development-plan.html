The honest summary

The iOS app is the product and it is good. Its PNR path is correctly gated so the simulator never answers a real lookup, its rail geometry rule holds everywhere with no violations, its IST date maths is correct across day rollovers, and it has no retain cycles. That is a real foundation.

Three things stand between it and a launch. The seeded delay simulator reaches surfaces it should not, most seriously by inventing a waitlist status for confirmed tickets on the lock screen. The marketing site promises capabilities that do not exist, including machine learning that appears nowhere in the codebase. And the whole product rests on one unofficial endpoint with no fallback.

The decision that shapes everything else

Stay device-local. Do not build accounts.

There is no authentication anywhere in the repo today, and the plan below assumes you keep it that way. Nothing in the feature set needs a user record: PNR watching already runs on-device against a free feed, and the Logbook is pure derivation over a local JSON file. Accounts would also invert your best differentiator, since both /privacy and /about lead on the claim that trips never leave the device.

If you disagree, this is the moment to say so. Choosing accounts adds an identity provider, an entitlements file that does not exist yet, a database, route protection, a durable rate-limit store, and a privacy-policy rewrite. It also forces a reconciliation layer, because the iOS and web trip stores are already schema-incompatible: iOS encodes addedAt as a Swift reference date while web uses epoch milliseconds. That is roughly four weeks of work that buys nothing a user asked for. If cross-device sync matters later, CloudKit private database gets you there with no login screen and no policy change.

Phase 4 Own the data 3 weeks

Everything rests on one unofficial endpoint. erail is the sole source of schedules, routes, platforms, per-halt times, track kilometres, and every station coordinate in the system. A single rule at its edge takes down both apps.

TaskDetailPriority
Snapshot the schedules into your own store erail's value is 4,022 timetables that change a few times a year, not a live feed. Pull them on a schedule, serve from your own store, and treat erail as a refresh source rather than a request-path dependency. This converts an outage from "product down" to "data one revision stale". Critical
Collapse three parsers into one The same delimited erail response is parsed by hand in TypeScript, Swift, and Python, with three different sets of positional indices and three different validation rules. They already disagree: the web rejects rows iOS renders, and the Python build tool validates nothing. Make the server the only thing that talks to erail and give iOS a stable JSON contract, so drift is fixable without an App Store review. Critical
Build a catalog rebuild tool Nothing regenerates ir-trains.json or stations.json. Both copies are kept byte-identical by hand and carry no date or version field, so the snapshot decays from day one with nothing to surface it. Add generatedAt and deduplicate the 42 colliding station codes. High
Rate-limit every route and add a circuit breaker Five of six routes have no limit. health makes two live upstream calls on every request, and train/[no] up to six on a cold miss, both unauthenticated. There is no breaker, so a blocking upstream gets hammered. High
Make the health check detect drift It probes trainInfo, which never touches the route endpoint, so drift in the parser feeding all coordinates and geometry reports green. And it counts an invalid-PNR rejection as healthy, so the entire passenger and coach parse path is never validated. Probe fullTrain and assert response shape. High
Fix the delay-history dataset It is billed as the raw material for delay prediction and is currently fed the simulator's own output with no field marking it simulated, on an ephemeral filesystem, into a git-tracked file. Any model trained on it learns the PRNG. Record real observations only, and move it off the ephemeral disk. High
Rotate the shared device fingerprint confirmtkt.ts:55 generates one DEVICE_ID per process, so every web user shares one identity upstream. That is an efficient way to get the endpoint blocked. Medium
Done when Blocking erail at the firewall degrades the product to stale schedules instead of breaking it, one parser exists, the health endpoint fails when a parser drifts, and a scheduled job keeps the catalog current with a visible generation date.

Phase 7 After launch Ongoing

Everything here depends on having real users and real observations, so none of it can start earlier however tempting it looks.

  • Delay prediction, for real. Once phase 4's dataset holds genuine observations rather than simulator output, the moat becomes buildable. Not before: a model trained on today's file learns the PRNG.
  • Geometry coverage beyond 12 trains. The pipeline works and 12 of its 19 misses were transient Overpass timeouts, not geometry problems. Widen the seed set and rerun. Remember the segment file is a build-time resource, so extending coverage needs an app release, and delete legkm.json whenever the seed set changes or the corridor sanity gate silently disables itself for new legs.
  • Home screen and lock screen widgets. Needs an App Group, which does not exist yet, because the extension currently cannot read the app's trips.
  • Platform-change and delay notifications. Currently promised in Settings and across five site pages, with no implementation. Phase 2 removes the promise; this builds it.
  • Apple Watch. Already correctly labelled Coming Soon in Settings.
  • Architecture paydown. Roughly 790 lines out of TripDetailView.swift into four files, AddTripView.swift split into the four screens it actually contains, and LogStats pulled out of LogbookView.swift first because it is where the provenance flag lands.

What the product looks like at the end

railly.app

A marketing site whose every sentence is true, plus three real tools.

  • PNR status. Type a real PNR, see the real booking, per-passenger current status, coach, berth, quota, chart state, and the live rake formation. Real errors when the PNR is wrong.
  • RailLens. Any of 4,022 services drawn on a real map, with real track geometry where it exists and a per-route caveat naming exactly which legs are drawn straight.
  • Train and station reference. Real timetables, honest sample boards, no invented statistics.
  • No /app. The product is the iOS app. The site sells it and does the one job a browser does better, which is a quick PNR check without installing anything.

Railly for iPhone

The same app it is now, with the lying removed and the live data plugged in.

  • My Trips over a live network map, every number carrying a visible Live or Estimated badge driven by its own provenance.
  • Trip detail with the travelled route solid and the rest dashed, on real OpenStreetMap track, with the drawn line and the tracked position guaranteed to be the same geometry.
  • PNR with real status from a source ladder, never a simulated answer, and coach position from the actual chart.
  • Live Activities that never invent a waitlist status, that fit the lock screen on a measured device rather than a guess, and that carry the provenance badge.
  • Passport logbook whose lifetime totals are computed from real track kilometres, with no refund claims built on estimates.
  • Seat availability from a real feed, with the fill model as a labelled fallback.
  • Device-local by design. No account, no login, working export and import, and a delete that actually deletes.

What gets deleted

Subtraction is most of the plan, so it is worth listing explicitly. None of this is a feature you lose; all of it is something currently claiming to exist.

  • The web /app lane four routes, orphaned, capped at 12 trains, auto-seeding fake trip history
  • Star ratings on testimonials the archetypes and the illustrative label stay
  • "8 trains watched" and the word live on LiveBoard
  • The machine-learning, inbound-rake, and control-room-bulletin claims
  • Invented per-station operational strings and the 14m network delay tile
  • The all-green competitor comparison column
  • Four pricing tiers, gift cards, and family sharing unless StoreKit ships in phase 6
  • The blanket honesty claim in llms.txt restored once it becomes true
  • The simulator's invented events, platform changes, and speed jitter
  • Four write-only Settings toggles
  • 96 MB of committed and uncommitted Overpass cache
  • Dead code trains.ts duplicating the seed data, bearing, trainByNumber, searchStations, stationByCode, the unreachable booking path, Analytics.recent()

How to tell it is working

  • After phase 0. A fresh clone builds and draws a full-geometry route. Nothing important lives on one laptop.
  • After phase 1. Every screen and page can be read by a stranger who then believes only true things. llms.txt can be restored verbatim.
  • After phase 2. No control in Settings lies. Export and import round-trip a multi-passenger booking. A forced upstream 403 produces a truthful error.
  • After phase 3. Someone with no app installed checks a real PNR on the website and gets a real answer. The site's central claim is now a fact.
  • After phase 4. Blocking erail degrades the product instead of breaking it.
  • After phase 5. Live means live, Estimated means estimated, and the badge comes from the data.
  • After phase 6. CI green on every push, privacy manifest shipped, build in review.
